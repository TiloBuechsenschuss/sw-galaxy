# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this project is

**SW Galaxy** is a static, client-side single-page web app that lets Star Wars FFG
(*Edge of the Empire* / *Age of Rebellion* / *Force and Destiny*) role players search and
filter weapons, armor, gear, species and item attachments. It is deployed as a plain
static site on GitHub Pages: <https://applifaction.github.io/sw-galaxy>

There is **no build step, no package manager, no test suite and no CI**. What is in the
repo is what gets served. Committed files are the deployment artifact.

## Tech stack

- **AngularJS 1.6.2** (not Angular 2+) — loaded from the Google CDN in `index.html`
- **Angular Material 1.1.x** — `js/angular-material.js` and `css/angular-material.min.css`
  are served from this repo (a former gitcdn URL disappeared; see commit `b3d1de6`)
- **md-data-table** and **angular-fixed-table-header** — vendored under `bower_components/`
- **PHP 7+ CLI** — only for the offline XML→JSON data conversion, not for serving the app
- Custom webfont `eote_symbolregularmod` (`font/eote-symbol/`) renders the FFG dice symbols

### Third-party hosting is the recurring failure mode

Assets loaded from someone else's host have died twice now and taken the app with them:
the Angular Material stylesheet on gitcdn (fixed in `b3d1de6` by vendoring it), and a
CodePen-hosted `svg-assets-cache.js` providing `material.svgAssetsCache`, which started
returning 403 (fixed by deleting it — see below). A dead `<script>` that registers an
AngularJS module is fatal, not degraded: the module never registers, `$injector:modulerr`
aborts bootstrap, and the page renders nothing at all.

**Vendor new third-party assets into the repo rather than hotlinking them.** The remaining
external dependencies are AngularJS itself on the Google CDN and the Material Icons
stylesheet on Google Fonts, so the app still needs an internet connection on first load.

## Architecture notes

### Data flow

1. OggDude Character Generator XML files are dropped into a folder under
   `xml_to_json/xml_sources/` (one folder per data set — currently just
   `oggdude`; any folder name works).
2. `xml_to_json/convert.php` globs `xml_sources/*/<FileName>.xml`, merges all sources,
   de-duplicates by the item's `Key`, attaches a `Thumbnail` path (falling back to
   `img/no_image.png` when no matching PNG exists) and writes `data/json/<Name>.json`.
   The JSON is shaped `{ "<TypeKey>": [ ...items ] }`.
   **Precedence follows the alphabetical glob order and the first `Key` wins**, so a
   folder that sorts earlier overrides later ones. One exception: an entry sourced
   *only* from a book in `$deprioritisedBooks` (the Unofficial Species Menagerie)
   always loses to one with an official book. Rows are then written sorted by their
   first `Source` book, then `Name`, then `Key`, so a regenerated export diffs cleanly.
3. `index.html` declares one `<div item-list>` per tab, passing `source-name` (the type
   key inside the JSON) and `source-url` (the JSON file).
4. The `itemList` directive's controller `$http.get`s that JSON, normalizes every item,
   pre-computes min/max ranges for the numeric sliders, and collects the distinct values
   used to populate the filter dropdowns.

Each tab in `index.html` also passes `keyDesc='data/json/ItemDescriptors.json'`. That file
does not exist and is not generated by `convert.php`. It is harmless: the directive binds
`keyDesc` into its isolate scope but never reads it, so nothing is ever fetched. Leave it
alone unless you are actually implementing the feature it was meant for.

### Read `xml_to_json/README.md` before touching data

That file is the full reference for the pipeline: the merge and precedence rules, the
scripts, the fact that **OggDude's species XML is a different schema from the one the app
reads** (and what translates between them), and the four `simplexml_load_string()` +
`JSON_NUMERIC_CHECK` quirks the output depends on. Any data work should start there.

The short version:

- `convert.php` is a *mechanical* XML→JSON conversion. It reshapes only one thing —
  `<Source Page="44">Book</Source>` becomes `<Source><Book/><Page/></Source>`, because
  SimpleXML drops attributes and the page numbers would otherwise be lost — so a source
  file must otherwise already be in the app's schema.
- `xml_to_json/convert.py` is a Python port for machines without PHP. **The two must
  produce identical output** — change one, change the other.
- `xml_to_json/oggdude_species_to_app.py` translates OggDude's per-species XML into the
  app schema, resolving skill/talent keys to display names.
- `xml_to_json/verify_convert.py` rebuilds every JSON from the committed XML and checks
  the schema mapping against the shipped data. Run it after touching any of the three.

Recognized XML file names are fixed in `$validFileNames` in `convert.php`:
`Armor.xml`, `Weapons.xml`, `ItemAttachments.xml`, `Gear.xml`, `Species.xml`.
Adding a new data type means touching `convert.php`, `index.html`, and usually
`items.html`.

### Source selection defaults

The "Source" sidenav filter is a multi-select listing every Book name found in the loaded
data. By default all of them are selected except those named in the `defaultDisabledSources`
constant at the top of `SWApp.js` — currently `Unofficial Species Menagerie`. Disabled-by-
default sources still appear in the dropdown, so they can be switched on by choice.

`$scope.getDefaultSources()` builds that default selection and is used both on load and by
`resetFilters()`, so "Clear filters" returns to the default rather than selecting everything.
Note that it returns a fresh array, keeping `$scope.sources` (the list of available options)
independent of `$scope.filters.source` (the current selection).

Items are matched with `arrayFulltextFilterOr`, so an item is hidden only when *all* of its
sources are deselected — anything also printed in an official book stays visible.

### The filter layer

Most of `SWApp.js` is AngularJS filters. Two distinct groups:

- **Search/reduce filters** — `searchFilter`, `fulltextFilter`, `arrayFulltextFilter`,
  `arrayFulltextFilterOr`, `min`, `max`. These narrow the item array. They are chained
  in `$scope.filterItems()`, which runs inside a `$timeout` and feeds `$scope.filteredItems`.
  Results are paginated in JS: 10 shown initially, `increaseLimit()` adds 100, `showAll()`
  adds the rest.
- **Rendering filters** — `nameFilter`, `descriptionFilter`, `infoFilter`, `symbolFilter`,
  `qualityFilter`, `tooltipFilter`, `skillFilter`, `rangeFilter`, `modFilter`,
  `descriptorFilter`, `talentFilter`. These turn OggDude's markup and key codes into HTML.

The rendering filters produce HTML that is passed through `$sce.trustAsHtml`. The source
data is a trusted, committed artifact, so this is intentional — but it does mean any newly
introduced data source is effectively trusted code. Keep that in mind before wiring up
user-supplied or remote data.

`descriptorFilter` and `talentFilter` are long, flat lists of
`text.replace(/^KEY$/g, "Human readable name")` lines — several hundred of them. This is
the intended shape of the code: when the data contains a key with no mapping, the filters
log `Please add base mod mapping for: <KEY>` to the console. **Adding a missing mapping
means adding one more `text.replace` line in the right list, in the existing style** —
do not refactor these into lookup tables unless explicitly asked.

OggDude's inline markup handled by the rendering filters: `[H3]…[h3]`, `[H4]…[h4]`,
`[B]…[b]`, `[I]…[i]`, `[P]`, `[BR]`, and dice/symbol tokens such as `[ADVANTAGE]`/`[AD]`,
`[DIFFICULTY]`/`[DI]`, `[TRIUMPH]`/`[TR]` (see `symbolFilter` for the full set). Symbols
map to single characters of the `eote_symbolregularmod` font, wrapped in
`<span class='sw-symbol'>`.

## Conventions

- **ES5 only.** No `let`/`const`, arrow functions, template literals or `class`. The
  existing code uses `var`, hoisted loop counters (`var i, l = items.length`) and
  `function () {}`. Match it.
- **AngularJS 1.x DI by parameter name** — the code is not minification-safe (no
  `['$scope', ...]` array annotations). Do not introduce a minifier.
- Indentation is 4 spaces. Some blocks in `descriptorFilter`/`talentFilter` are
  tab-indented; leave them as they are rather than reflowing whole blocks.
- `==`/`!=` and `typeof x == 'string'` guards are the house style for the defensive checks
  around optional JSON fields.
- No linter or formatter is configured. Do not add one uninvited.

## Working on the data

- **Never hand-edit `data/json/*.json`.** They are generated. Edit the XML sources or
  the converter and re-run it.
- Regenerate with `python xml_to_json/convert.py` or `php xml_to_json/convert.php` from
  the repo root. Both write to `data/json/` relative to their own location, so they can
  be run from anywhere. `convert.py --check` reports without writing.
- Verify with `python xml_to_json/verify_convert.py`. It rebuilds every JSON file from
  the committed XML and fails if anything drifts.
- Both the XML sources and the generated JSON are committed — a data change is expected
  to include the regenerated JSON in the same commit.
- Item thumbnails go in `data/img/` and must be named `<TypeKey><Key>.png`, e.g.
  `ArmorHBA.png`, `GearBACKPACK.png`. The converter wires them up automatically on the
  next run; without a match the item falls back to `img/no_image.png`. Artwork for
  species and equipment is available in `oggdudes-data/SpeciesImages/` etc., named by
  bare `Key`, so it only needs the type prefix added.
- Output format is pretty-printed, 4-space indent, PHP-style escaped `\/`, ASCII-only,
  CRLF, no trailing newline. Both converters emit exactly that; don't reformat by hand.

## Verifying changes

There are no automated tests. Verification is manual:

1. Serve the repo root over HTTP (see `readme.md` — `file://` will not work, `$http.get`
   of the JSON is blocked by the browser).
2. Load the page and check each of the five tabs.
3. Open the browser console. It should stay quiet — `Please add base mod mapping for: …`
   and `debugging!` messages indicate unmapped data.
4. Exercise the sidenav filters, the search box, sorting and "show more"/"show all" on at
   least the Weapons tab, which has the most fields.
5. Angular Material is responsive; check a narrow viewport too. The app is explicitly
   optimized for phones, since players use it at the table.
